# Tools (`tool`)

Corresponds to `AgentTool` in upstream `types.ts` and the tool execution part of `agent-loop.ts`.

## `AgentTool` trait

Upstream's `AgentTool` is an object interface: it extends `Tool` (name, description, parameter schema) and adds `label`, `execute` and a few optional fields. delta uses a trait:

```rust
pub trait AgentTool: Send + Sync {
    fn definition(&self) -> &Tool;                                   // declaration sent to the model
    fn label(&self) -> &str { &self.definition().name }
    fn execution_mode(&self) -> Option<ToolExecutionMode> { None }
    fn output_schema(&self) -> Option<&Value> { None }
    fn replay(&self) -> Option<ToolReplay> { None }
    fn prepare_arguments(&self, arguments: JsonObject) -> JsonObject { arguments }
    fn execute(&self, arguments: Value, context: ToolContext)
        -> BoxFuture<'_, Result<AgentToolResult, ToolError>>;
}
```

| Upstream | delta | Notes |
| --- | --- | --- |
| `name`, `description`, `parameters` (inherited from `Tool`) | `definition() -> &Tool` | Reuses `delta_ai::Tool` directly, including `constrained_sampling` |
| `label` | `label()` | Defaults to the tool name |
| `executionMode` | `execution_mode()` | If any called tool is `Sequential`, the whole batch runs sequentially |
| `outputSchema` | `output_schema()` | Declaration only; the loop does not validate it |
| `replay` | `replay()` | `ToolReplay::{Never, Safe}`, for hosts with durable execution; the loop does not read it |
| `prepareArguments` | `prepare_arguments()` | Processes raw arguments before schema validation |
| `execute(toolCallId, params, signal, onUpdate)` | `execute(arguments, ToolContext)` | See below |

Tools are stored as `Arc<dyn AgentTool>` in `AgentContext::tools` and `AgentState::tools`.

### `ToolContext`

The positional parameters of upstream `execute` are merged into one struct:

```rust
pub struct ToolContext {
    pub tool_call_id: String,
    pub cancel: CancellationToken,   // cancellation token of this run
    pub updates: ToolUpdates,        // upstream's onUpdate callback
}
```

`ToolUpdates::send(partial)` emits a `ToolExecutionUpdate` event. It is the sender of an unbounded channel, so the tool does not need to await. All updates sent before `execute` returns are delivered (the channel is drained after return). Calls after return are ignored, consistent with upstream ("`onUpdate` has no effect after the tool finishes"). `ToolUpdates::none()` is for calling a tool directly outside the loop.

### Failure

`execute` returns `Err(ToolError)` (`Box<dyn Error + Send + Sync>`), which corresponds to throwing upstream: the loop records `AgentToolResult::error(err.to_string())` with `is_error = true`. A tool can also return a result with `is_error: true` to keep `details`.

## Convenience implementations

### `FnTool`

Declaration plus closure:

```rust
let tool = FnTool::new(Tool::new("echo", "Echo the input", schema), |args, _ctx| async move {
    Ok(AgentToolResult::text(args["text"].as_str().unwrap_or_default()))
})
.with_label("Echo")
.with_execution_mode(ToolExecutionMode::Sequential);
```

### `typed_tool` (feature `schemars`, on by default)

Arguments are a Rust type. The schema is generated by `schemars`, and arguments are deserialized after validation passes:

```rust
#[derive(Deserialize, JsonSchema)]
struct GetTime {
    /// IANA timezone name.
    timezone: Option<String>,
}

let tool = typed_tool("get_time", "Get the current time", |args: GetTime, _ctx| async move {
    Ok(AgentToolResult::text(format!("12:00 in {}", args.timezone.unwrap_or_else(|| "UTC".into()))))
});
```

`schema_for::<T>()` produces the shape a tool schema needs: draft-07, subschemas inlined (no `$ref`/`definitions`, because some providers do not support references), with `$schema` and the root `title` removed. Upstream builds schemas at runtime with TypeBox; the Rust equivalent is deriving them from types.

## Steps of one tool call

Same as upstream. Each call goes through these steps in order:

1. **Find the tool**: look it up by name in `context.tools`. If not found, record the error result `Tool {name} not found`.
2. **`prepare_arguments`**: process the raw arguments.
3. **Validate**: `delta_ai::validation::validate_tool_arguments`, including upstream's type coercion (numeric strings to numbers and so on). On failure, the error text is sent to the model.
4. **`before_tool_call` hook**: can block execution. If the run has been cancelled when the hook returns, record `Operation aborted`.
5. **Execute**: `execute`; forward `ToolExecutionUpdate` meanwhile and record the duration.
6. **`after_tool_call` hook**: overrides the result field by field.
7. **Emit events**: `ToolExecutionEnd`, then `MessageStart`/`MessageEnd` for the tool result message.

Calls that fail in steps 1–4 do not run, and `duration_ms` is `None`.

### Sequential and parallel

- **Sequential**: each call goes through all steps before the next one starts. After the run is cancelled, no new call starts.
- **Parallel** (default): first do steps 1–4 in order (`ToolExecutionStart` is emitted in source order), then run the calls that passed concurrently. `ToolExecutionEnd` is emitted in completion order; tool result messages are emitted in source order.
- When the reply stopped because of `length`, the arguments of every tool call may be truncated. The loop records an error result for each call directly and does not run them (upstream behavior).

### `run_tool_call`

A tool that calls other tools (for example upstream `examples/mcp-codemode`) runs nested calls with `run_tool_call`. It goes through the same steps 1–6, so hooks also apply to nested calls, but it emits no events and produces no messages. Failures come back as a result with `is_error`. The tool's intermediate results go to `RunToolCallOptions::on_update` (upstream `onUpdate`).

## Differences from upstream

- A trait instead of an object interface; the positional parameters of `execute` are merged into `ToolContext`.
- The parameter schema is `serde_json::Value` (upstream uses a TypeBox object). `typed_tool` offers a typed way to write it.
- `details` is `Option<Value>`; upstream uses a generic `TDetails`. Applications that need types serialize/deserialize themselves.
